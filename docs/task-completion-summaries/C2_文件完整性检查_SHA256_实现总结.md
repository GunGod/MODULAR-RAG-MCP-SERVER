## 使用示例

```python
from src.libs.loader import SQLiteIntegrityChecker

# 创建检查器
checker = SQLiteIntegrityChecker()

# 计算文件哈希
file_hash = checker.compute_sha256("/path/to/document.pdf")

# 检查是否跳过
if not checker.should_skip(file_hash):
    # 处理文件
    try:
        process_document()
        checker.mark_success(file_hash, "/path/to/document.pdf")
    except Exception as e:
        checker.mark_failed(file_hash, str(e))

# 关闭连接
checker.close()

# 或使用 context manager
with SQLiteIntegrityChecker() as checker:
    file_hash = checker.compute_sha256("/path/to/document.pdf")
    if checker.should_skip(file_hash):
        print("文件已处理，跳过")
```

## 附录：WAL 模式详解

### 什么是 WAL？

**WAL** (Write-Ahead Logging) 是数据库和存储系统中的一种**预写式日志**机制。

### 核心概念

**WAL** 要求在对数据文件进行修改之前，先写入日志记录。

```
传统方式（无 WAL）：
修改数据 → 写入磁盘
         ↓
      如果崩溃 → 数据丢失 ❌

WAL 方式：
写日志 → 写入磁盘 → 修改数据
        ↓
     如果崩溃 → 可以从日志恢复 ✅
```

### 工作流程

```
1. 客户端请求写入
   ↓
2. 先将修改写入 WAL 日志（追加到日志文件末尾）
   ↓
3. 将日志刷到磁盘
   ↓
4. 修改实际数据
   ↓
5. 返回成功
```

### 为什么需要 WAL？

#### 场景 1：崩溃恢复
```
时间线：
10:00 - 开始事务：转账 100 元
10:01 - 写入 WAL：{from: A, to: B, amount: 100}
10:02 - WAL 刷盘成功 ✅
10:03 - 修改数据：A 账户 -100
       修改数据：B 账户 +100
10:04 - 系统崩溃 💥

重启后：
- 检查 WAL 日志
- 发现已提交但未完成的事务
- 重放日志：A-100, B+100
- 数据恢复到一致状态 ✅
```

#### 场景 2：性能优化
```
传统方式：
- 每次写操作都要随机写入磁盘不同位置
- 磁盘寻道时间长，性能差

WAL 方式：
- 日志是顺序追加写入（append-only）
- 顺序写入比随机写入快得多
- 后台异步将修改应用到数据文件
```

### WAL 模式 vs 其他模式

| 特性 | WAL 模式 | 回滚日志 | 无日志 |
|------|----------|----------|--------|
| **写入方式** | 先写日志再改数据 | 写数据前备份 | 直接写数据 |
| **崩溃恢复** | ✅ 支持 | ✅ 部分 | ❌ 不支持 |
| **性能** | ⚡ 快（顺序写） | 🐢 慢（写两遍） | ⚡⚡ 最快 |
| **数据安全** | ✅ 高 | ✅ 高 | ❌ 低 |
| **存储开销** | 小（仅日志） | 大（完整副本） | 无 |

### 常见数据库的 WAL 实现

#### SQLite WAL 模式
```bash
# 启用 WAL 模式
PRAGMA journal_mode=WAL;

# 文件结构
database.db       # 主数据库文件
database.db-wal   # WAL 日志文件
database.db-shm   # 共享内存索引
```

**优势**：
- 读写并发（读操作不阻塞写操作）
- 更快的提交速度
- 更好的崩溃恢复

#### PostgreSQL WAL
```postgresql
# 配置参数
wal_level = replica        # WAL 级别
fsync = on                 # 强制刷盘
wal_buffers = 16MB         # WAL 缓冲区
```

#### MySQL InnoDB Redo Log
```ini
[mysqld]
innodb_log_file_size = 48M    # Redo log 文件大小
innodb_flush_log_at_trx_commit = 1  # 每次事务提交刷盘
```

### WAL 日志内容示例

```
[LSN: 12345] TXN_START, txn_id=1001
[LSN: 12346] UPDATE, table=users, id=5, old_name="Alice", new_name="Bob"
[LSN: 12347] INSERT, table=orders, id=999, user_id=5, amount=100
[LSN: 12348] TXN_COMMIT, txn_id=1001
[LSN: 12349] CHECKPOINT, flush_to_data_file=true
```

**LSN** = Log Sequence Number（日志序列号），递增的序号

### WAL 的权衡

#### ✅ 优点
1. **数据安全**：崩溃可恢复
2. **性能高**：顺序写入
3. **并发友好**：读写分离
4. **备份支持**：基于时间点恢复

#### ⚠️ 缺点
1. **额外存储**：需要日志文件空间
2. **写入放大**：写日志 + 写数据 = 写两次
3. **检查点开销**：定期需要将日志应用到数据文件
4. **配置复杂**：需要调整日志大小、刷盘策略等

### 在本项目中的应用

在 `SQLiteIntegrityChecker` 中启用 WAL 模式提升并发性能：

```python
# 启用 WAL 模式
self.conn.execute("PRAGMA journal_mode=WAL")
self.conn.execute("PRAGMA synchronous=NORMAL")
```

这使得多个进程可以同时读取数据库，提高 Ingestion Pipeline 的并发处理能力。

### 总结

| 方面 | 说明 |
|------|------|
| **全称** | Write-Ahead Logging |
| **原理** | 修改数据前先写日志 |
| **目的** | 崩溃恢复 + 性能优化 |
| **特点** | 顺序写入、原子性、持久性 |
| **应用** | SQLite、PostgreSQL、MySQL、MongoDB 等 |
| **ACID 关系** | 主要保证 A（原子性）和 D（持久性） |

**一句话总结**：
> WAL 就像是"存档文件"——玩游戏前先存档，如果游戏崩溃了，可以从存档点恢复，不会丢失进度。
