## 创建的文件

### 1. `src/core/types.py`
**作用**: 定义核心数据类型，作为全系统的数据契约中心

**关键内容解读**:

#### `ImageMetadata` 数据类
- **作用**: 封装图片在文档中的元信息
- **字段**:
  - `id`: 全局唯一图片标识符（格式：{doc_hash}_{page}_{seq}）
  - `path`: 存储路径（data/images/{collection}/{image_id}.png）
  - `page`: 页码（可选）
  - `text_offset`: 占位符在 Document.text 中的起始位置
  - `text_length`: 占位符长度
  - `position`: 物理位置信息（可选）
- **方法**: `to_dict()`, `from_dict()` 用于序列化
- **验证**: `__post_init__` 确保 id 和 path 非空，偏移量非负

#### `Document` 数据类
- **作用**: 表示摄取的文档，包含文本和元数据
- **字段**:
  - `id`: 唯一文档标识符（通常为 SHA256 哈希）
  - `text`: 完整文本内容（可能包含图片占位符）
  - `metadata`: 元数据字典（**必须包含 source_path**）
  - `created_at`, `updated_at`: 时间戳（自动生成）
- **metadata 要求**:
  - **source_path**: 原始文件路径（必需）
  - **images**: 图片元数据列表（可选，List[ImageMetadata]）
  - 其他字段可扩展（title, author 等）
- **图片占位符**: `[IMAGE: {image_id}]`
- **方法**:
  - `to_dict()`, `to_json()`: 序列化
  - `from_dict()`, `from_json()`: 反序列化
  - `generate_id(content)`: 生成 SHA256 文档 ID
  - `get_images()`: 获取图片元数据列表

#### `Chunk` 数据类
- **作用**: 文档的一个片段，包含位置信息
- **字段**:
  - `id`: 唯一片段标识符（格式：{doc_id}_{index:04d}_{hash}）
  - `text`: 片段文本
  - `metadata`: 元数据（继承自 Document，可扩展）
  - `start_offset`, `end_offset`: 在原文档中的字符位置
  - `source_ref`: 源文档引用
- **方法**:
  - `to_dict()`, `to_json()`: 序列化
  - `from_dict()`, `from_json()`: 反序列化
  - `generate_id(doc_id, index, text)`: 生成片段 ID
  - `get_size()`: 获取片段字符数

#### `ChunkRecord` 数据类
- **作用**: 带向量的片段，用于存储和检索
- **字段**:
  - 继承 Chunk 的所有字段
  - `dense_vector`: 稠密向量（用于语义搜索）
  - `sparse_vector`: 稀疏向量（用于 BM25 搜索）
- **方法**:
  - `from_chunk(chunk, dense_vector, sparse_vector)`: 从 Chunk 创建
  - `to_chunk()`: 转换为 Chunk（丢弃向量）
  - `has_dense_vector()`, `has_sparse_vector()`: 检查向量是否存在
- **验证**: metadata 必须包含 source_path（用于引用生成）

## 关键设计解读

### Q1: 为什么需要中心化的数据类型定义？

**解释**:
在大型系统中，数据类型散落在各模块会导致：
- 重复定义（DRY 原则违反）
- 字段不一致（模块 A 用 `file_path`，模块 B 用 `source`）
- 序列化格式不统一
- 难以维护和重构

**解决方案**:
将核心数据类型集中在 `src/core/types.py`，作为"数据契约中心"：
- **单一真实来源**（Single Source of Truth）
- **稳定的序列化格式**
- **清晰的验证逻辑**
- **易于扩展**

**类比**:
就像建筑物中的"承重墙"，所有房间都依赖它。如果需要修改，只需在一处修改，所有房间都会受益。

**好处**:
- **类型安全**: 所有模块使用相同的数据结构
- **减少耦合**: 模块间通过契约通信，而非直接依赖
- **易于测试**: 只需测试数据类型一次
- **便于重构**: 修改数据结构只需改一处

### Q2: 为什么 metadata.images 使用 List[Dict] 而不是 List[ImageMetadata]？

**解释**:
实际上我们的实现**同时支持两种格式**：
1. **ImageMetadata 对象**: 面向对象，有类型检查和方法
2. **字典**: 面向序列化，直接可 JSON 化

**实现方式**:
```python
def get_images(self) -> List[ImageMetadata]:
    images_data = self.metadata.get("images", [])
    images = []
    for img_data in images_data:
        if isinstance(img_data, ImageMetadata):
            images.append(img_data)
        elif isinstance(img_data, dict):
            images.append(ImageMetadata.from_dict(img_data))
    return images
```

**好处**:
- **灵活性**: 用户可以选择任一格式
- **向后兼容**: 字典格式可直接从 JSON 加载
- **类型安全**: 对象格式提供方法和验证
- **最佳实践**: 推荐使用 ImageMetadata 对象

### Q3: 为什么图片占位符使用 [IMAGE: {id}] 格式？

**解释**:
图片占位符需要在文本中标记图片位置，同时：
- **易于解析**: 正则表达式可轻松匹配
- **人类可读**: 在文本中清晰可见
- **唯一标识**: 通过 id 引用 ImageMetadata
- **避免冲突**: 特殊格式减少误匹配

**规范**:
```
[IMAGE: {image_id}]
```

**示例**:
```python
text = "这是一个包含图片的文档。[IMAGE: abc123_page1_0000] 这是图片后的内容。"
```

**关联**:
```python
images = [
    ImageMetadata(
        id="abc123_page1_0000",
        path="data/images/default/abc123_page1_0000.png",
        text_offset=18,  # "[IMAGE: abc123_page1_0000]" 的起始位置
        text_length=30   # 占位符长度
    )
]
```

**好处**:
- **精确定位**: 通过 text_offset 找到占位符位置
- **可替换**: 运行时可以将占位符替换为其他内容
- **可搜索**: 支持搜索图片周围的文本

## 使用示例

### 示例 1: 创建文档

```python
from src.core.types import Document

# 创建简单文档
doc = Document(
    id="abc123",
    text="This is a test document.",
    metadata={"source_path": "/path/to/doc.pdf"}
)

# 创建带图片的文档
doc_with_images = Document(
    id="def456",
    text="Document with [IMAGE: img_001] an image.",
    metadata={
        "source_path": "/path/to/document.pdf",
        "title": "Sample Document",
        "images": [
            {
                "id": "img_001",
                "path": "data/images/default/img_001.png",
                "page": 1,
                "text_offset": 14,
                "text_length": 17,
                "position": {"x": 100, "y": 200, "width": 800, "height": 600}
            }
        ]
    }
)
```

### 示例 2: 创建 Chunk

```python
from src.core.types import Chunk

# 创建片段
chunk = Chunk(
    id="abc123_0000_a1b2c3",
    text="This is the first chunk.",
    metadata={
        "source_path": "/path/to/doc.pdf",
        "chunk_index": 0
    },
    start_offset=0,
    end_offset=24,
    source_ref="abc123"
)

# 生成 Chunk ID
doc_id = "abc123"
chunk_id = Chunk.generate_id(doc_id, index=0, text="First chunk")
# Returns: "abc123_0000_<8-char-hash>"
```

### 示例 3: 创建 ChunkRecord

```python
from src.core.types import Chunk, ChunkRecord

# 从 Chunk 创建 ChunkRecord
chunk = Chunk(
    id="abc123_0000_a1b2c3",
    text="Searchable chunk.",
    metadata={"source_path": "/path/to/doc.pdf"},
    start_offset=0,
    end_offset=16,
    source_ref="abc123"
)

# 添加向量
record = ChunkRecord.from_chunk(
    chunk,
    dense_vector=[0.1, 0.2, 0.3, ...],  # 1536-dim vector
    sparse_vector={"searchable": 0.5, "chunk": 0.3}
)

# 转换回 Chunk
chunk_from_record = record.to_chunk()
```

### 示例 4: 序列化

```python
# 序列化为 dict
doc_dict = doc.to_dict()

# 序列化为 JSON
doc_json = doc.to_json(indent=2)

# 反序列化
doc2 = Document.from_dict(doc_dict)
doc3 = Document.from_json(doc_json)
```

### 示例 5: 图片处理

```python
# 获取文档中的所有图片
images = doc.get_images()

for image in images:
    print(f"Image ID: {image.id}")
    print(f"Path: {image.path}")
    print(f"Position in text: {image.text_offset} - {image.text_offset + image.text_length}")

# 通过 text_offset 找到占位符
if doc.text:
    placeholder = doc.text[image.text_offset:image.text_offset + image.text_length]
    print(f"Placeholder: {placeholder}")  # [IMAGE: img_001]
```
