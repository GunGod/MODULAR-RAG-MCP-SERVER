## 🔑 关键设计解读

### Q1: 为什么要引入 TextChunk？
**解释**：原始实现返回 `List[str]`，位置信息在切分后丢失。下游 DocumentChunker 需要用启发式算法估算位置，导致：
- 位置不精确（基于 chunk_index * 1000 估算）
- 重复内容误匹配（`str.find()` 可能找错位置）
- 无法考虑 overlap 的实际位置影响

**TextChunk 的解决方案**：
- ✅ Splitter 直接返回精确位置
- ✅ 无需估算，位置准确
- ✅ 支持 overlap 的位置追踪
- ✅ 类型安全（位置验证）

**类比**：
- 旧方式：就像快递单只写了"3号楼"，你需要去估算具体位置
- 新方式：快递单写了完整地址"3号楼201室"，精确无误

### Q2: _split_recursive 中的 base_offset 参数是如何工作的？
**解释**：`base_offset` 表示当前待切分文本在**原始文档**中的起始位置，在递归调用中需要正确传递和维护。

**递归位置追踪机制**：
```python
def _split_recursive(text, separator_index, base_offset):
    chunks = []
    current_start = base_offset  # ← 从 base_offset 开始追踪

    for split in splits:
        if len(current) + len(split) > chunk_size:
            # 保存当前 chunk
            chunk = TextChunk(
                text=current,
                start_offset=current_start,      # ← 使用追踪的位置
                end_offset=current_start + len(current)
            )
            chunks.append(chunk)

            # 更新追踪位置
            current_start += len(current)

            # 如果新 chunk 太大，递归切分
            if len(new_chunk) > chunk_size:
                sub_chunks = _split_recursive(
                    new_chunk,
                    separator_index + 1,
                    current_start  # ← 传递当前位置！
                )
                # 从最后一个子块恢复位置
                current_start = sub_chunks[-1].start_offset
```

**关键点**：
1. **初始化**：`current_start = base_offset`（从传入的位置开始）
2. **累积更新**：每次保存 chunk 后，`current_start += len(current)`
3. **递归传递**：递归时传递 `current_start`，确保子块位置正确
4. **位置恢复**：递归返回后，从最后一个子块恢复 `current_start`

**示例**（3000 字符文档，chunk_size=1000）：
```
第 1 层（\n\n 切分）：
  text = "A" * 3000
  base_offset = 0
  → 整个文本太大，递归

第 2 层（\n 切分）：
  text = "A" * 3000
  base_offset = 0  # 继承自上层
  → 还是没有 \n，递归

第 3 层（空格切分）：
  text = "A" * 3000
  base_offset = 0  # 继承自上层
  → 还是没有空格，递归

第 4 层（字符切分）：
  text = "A" * 3000
  base_offset = 0  # 继承自上层
  → _split_by_size(text, 0)
  → 返回 3 个 chunk：
     TextChunk("A"*1000, start=0, end=1000)
     TextChunk("A"*1000, start=1000, end=2000)
     TextChunk("A"*1000, start=2000, end=3000)
```

### Q3: Overlap 的作用机制与策略选择

#### Overlap 的核心价值

在 RAG 系统中，overlap 是为了解决"语义边界被硬切断"的问题：

**问题场景**：
```python
# 文档内容
"梯度下降是机器学习中最常用的优化算法之一。它通过迭代更新参数来最小化损失函数。具体来说，梯度下降利用损失函数关于参数的梯度信息，沿着梯度的反方向更新参数。"

# 无 overlap 切分（chunk_size=50）
chunk[0] = "梯度下降是机器学习中最常用的优化算法之一。它通过迭代更新参数来最小化损"  # 被截断！
chunk[1] = "失函数。具体来说，梯度下降利用损失函数关于参数的梯度信息，沿着梯度的反方向更新参数。"

# 用户查询："梯度下降如何更新参数？"
# → 召回 chunk[0]，但被截断，看不到完整答案
```

**有 Overlap 的效果**：
```python
# 有 overlap 切分（chunk_size=50, overlap=20）
chunk[0] = "...最小化损失函数。具体来说，梯度下降利用损失函数关于参数的梯"  # 包含完整句子
chunk[1] = "损失函数。具体来说，梯度下降利用损失函数关于参数的梯度信息，沿着梯度的反方向更新参数。"

# 用户查询："梯度下降如何更新参数？"
# → 召回 chunk[0]，可以看到完整答案
```

#### Overlap 的核心作用

| 作用 | 说明 | 示例 |
|------|------|------|
| **语义缓冲** | 避免关键信息在边界被硬切断 | 句子 "因此，我认为这个..." 保持完整 |
| **召回保险** | 关键信息出现在多个 chunk，提高召回率 | "监督学习" 可能出现在 chunk[0] 和 chunk[1] |
| **上下文连贯** | 每个 chunk 都有上下文，减少"断章取义" | 避免 "但它是" 这样的无主语片段 |

#### Overlap 的权衡

**收益** ✅：
- 语义完整性 ↑
- 召回率 ↑
- 用户体验 ↑（返回的答案更自然）

**代价** ❌：
- 存储成本 ↑（总数据量增加）
- 计算成本 ↑（向量化和检索时处理更多文本）
- Token 消耗 ↑（LLM 处理冗余信息）

#### 经验法则

```
overlap ≈ chunk_size × (10% ~ 20%)

典型配置：
- 技术文档：chunk_size=1000, overlap=200 (20%)
- 新闻文章：chunk_size=500, overlap=50 (10%)
- 法律合同：chunk_size=1500, overlap=300 (20%)
```

#### 我们的 Overlap 策略：保留语义边界

**当前实现的特点**：
```python
def _apply_overlap(self, chunks: List[TextChunk]) -> List[TextChunk]:
    for i in range(1, len(chunks)):
        # 从前一个 chunk 的末尾取 overlap
        overlap_text = chunks[i-1].text[-self.chunk_overlap:]

        # 直接拼接，保留完整的分隔符
        overlapped_text = overlap_text + chunks[i].text
```

**示例结果**：
```python
# 输入文档："AAAA\n\nBBBB\n\nCCCC"
chunk_size = 10, overlap = 3

# 无 overlap 切分
chunks = [
    TextChunk("AAAA\n\n", 0-6),
    TextChunk("BBBB\n\n", 6-12),
    TextChunk("CCCC", 12-16)
]

# 应用 overlap
chunks = [
    TextChunk("AAAA\n\n", 0-6),
    TextChunk("\n\nBBBB\n\n", 4-13),  # ← 包含完整的 "\n\n"
    TextChunk("\n\nCCCC", 11-18)     # ← 包含完整的 "\n\n"
]
```

**选择这个方案的原因**：

1. **语义完整性优先**：对于 RAG 系统，保留段落边界（`\n\n`）比减少几个 token 更重要
2. **结构清晰**：overlap 部分包含完整的分隔符，便于理解文档结构
3. **适合场景**：我们的目标是处理技术文档、论文等，这些文档的语义单元通常与分隔符对齐

**适用场景**：
- ✅ 技术文档（Markdown、论文）
- ✅ 代码注释
- ✅ 法律合同
- ✅ 结构化报告

**不适用场景**（可以考虑其他方案）：
- ❌ 纯新闻文本（追求简洁，不需要结构边界）
- ❌ 对话记录（追求固定 overlap 大小）
- ❌ Token 成本敏感场景

#### 与 LangChain 的对比

| 方面 | LangChain 方式 | 我们的方式 |
|------|---------------|----------|
| **Overlap 时机** | 切分时就应用 | 切分后统一应用 |
| **Overlap 大小** | 固定字符数 | 包含完整分隔符（不固定） |
| **位置计算** | 基于字符偏移 | 基于文本拼接 |
| **代码复杂度** | 较简单 | 较复杂（位置追踪） |
| **语义完整性** | ⚠️ 可能破坏结构边界 | ✅ 保留语义边界 |
| **适用场景** | 通用文本处理 | RAG 系统、技术文档 |

### 第一版：返回 List[str]（原始版本）

**特点**：
```python
def split_text(self, text: str) -> List[str]:
    # 只返回文本，无位置信息
    chunks = []
    for split in splits:
        chunks.append(split)
    return chunks
```

**问题**：
- ❌ DocumentChunker 需要用启发式算法估算位置
- ❌ 位置不精确
- ❌ 重复内容可能误匹配

### 第二版：引入 TextChunk（当前版本）

**特点**：
```python
def split_text(self, text: str) -> List[TextChunk]:
    # 返回带位置信息的 TextChunk
    chunks = []
    current_start = base_offset

    for split in splits:
        chunk = TextChunk(
            text=split,
            start_offset=current_start,
            end_offset=current_start + len(split)
        )
        chunks.append(chunk)
        current_start += len(split)

    return chunks
```

**优势**：
- ✅ 位置精确，无需估算
- ✅ 支持递归位置追踪
- ✅ 便于调试和验证

### Overlap 策略的讨论与决策

#### 讨论 1：Overlap 是否应该包含分隔符？

**方案 A：包含分隔符（当前实现）**
```python
overlap_text = prev_chunk.text[-overlap_size:]
# 直接取最后 N 个字符，可能是 "\n\n"

# 结果：
chunk[1] = "\n\nBBBB\n\n"  # 包含完整分隔符
```

**优点**：
- ✅ 保留语义边界
- ✅ 便于理解文档结构
- ✅ 适合技术文档

**缺点**：
- ❌ overlap 大小不固定（取决于分隔符位置）
- ❌ 可能产生冗余（多个 `\n\n` 连在一起）

**方案 B：不包含分隔符（LangChain 方式）**
```python
start = end - overlap  # 固定偏移
chunk_text = text[start:end]

# 结果：
chunk[1] = "B\n\nCCCC"  # 不包含完整分隔符
```

**优点**：
- ✅ overlap 大小固定
- ✅ 不会重复分隔符

**缺点**：
- ❌ 可能破坏语义边界（"BBBB" 被切断）
- ❌ 语义完整性降低

**方案 C：智能 overlap（理想方案）**
```python
# 跳过前导空白，智能选择 overlap
overlap_text = prev_chunk.text[-overlap_size:].lstrip()
if len(overlap_text) < overlap_size // 2:
    overlap_text += curr_chunk.text[:overlap_size - len(overlap_text)]
```

**优点**：
- ✅ 兼顾语义完整性和 overlap 大小
- ✅ 灵活适应不同场景

**缺点**：
- ❌ 实现复杂
- ❌ 可能引入不确定性

#### 决策：选择方案 A（包含分隔符）

**理由**：
1. **RAG 系统特点**：我们的目标是处理技术文档、论文等，语义边界与分隔符高度相关
2. **用户场景**：用户通常按段落、章节进行查询，保留分隔符有助于理解
3. **可解释性**：包含完整分隔符的结果更易调试和理解
4. **实现复杂度**：方案 A 最简单，后续可根据实际需求调整

**适用场景验证**：
```python
# 技术文档场景
文档 = "# 机器学习概述\n\n机器学习是...\n\n# 核心算法\n\n梯度下降是..."

有 overlap 的结果：

chunk[1] = "\n\n# 核心算法\n\n梯度下降是..."   # 保留章节标题

# → 用户查询 "梯度下降" 时，chunk[1] 包含完整上下文
```

## 💡 关键设计决策记录

### 决策 1：引入 TextChunk 数据类

**背景**：
- 原始实现返回 `List[str]`，位置信息丢失
- DocumentChunker 需要用启发式算法估算位置
- 估算不准确，导致边界问题

**决策**：
- ✅ 引入 `TextChunk` 数据类，包含 `text`、`start_offset`、`end_offset`
- ✅ 修改 `BaseSplitter.split_text()` 返回类型为 `List[TextChunk]`
- ✅ 所有 splitter 实现必须返回位置信息

**收益**：
- 位置精确，无需估算
- 支持调试和验证
- 类型安全

**代价**：
- 需要修改所有 splitter 实现
- 数据类增加了少量内存开销

### 决策 2：Overlap 保留语义边界

**背景**：
- 有两种 overlap 策略：固定大小（LangChain）vs 保留分隔符（语义感知）
- 需要根据 RAG 系统的特点选择

**决策**：
- ✅ 采用"保留分隔符"策略
- ✅ overlap 直接从前一个 chunk 的末尾取，不跳过空白
- ✅ 结果：overlap 包含完整的分隔符（如 `\n\n`）

**理由**：
1. **语义完整性**：技术文档的语义单元通常与分隔符对齐
2. **结构保留**：保留段落、章节边界，便于理解
3. **召回优化**：语义完整的 chunk 更容易被检索到
4. **实现简单**：不需要复杂的空白跳过逻辑

**适用场景**：

## 🎯 使用建议

### 配置推荐

根据不同场景选择合适的参数：

| 场景 | chunk_size | overlap | 理由 |
|------|-----------|---------|------|
| **技术文档** | 1000-1500 | 15-25% | 保留段落边界，语义完整 |
| **代码文件** | 800-1200 | 10-20% | 代码块完整，函数不被切断 |
| **法律合同** | 1500-2000 | 20-30% | 条款连贯，避免歧义 |
| **新闻文章** | 500-800 | 5-10% | 段落独立，减少冗余 |
| **对话记录** | 600-900 | 10-15% | 上下文连贯，保留话题转换 |
| **短文档** (<1000 字符) | 文档长度 | 0 | 不需要切分 |

### 示例配置

```yaml
# config/settings.yaml

splitter:
  provider: recursive
  chunk_size: 1000      # 每块约 1000 字符
  chunk_overlap: 200    # 20% overlap，约 200 字符
  separators:
    - "\n\n"            # 优先按段落切分
    - "\n"              # 其次按行切分
    - " "               # 再按单词切分
    - ""                # 最后按字符切分（兜底）
```

### 代码示例

```python
from src.libs.splitter import RecursiveSplitter
from src.ingestion.chunking import DocumentChunker
from src.libs.loader import PdfLoader

# 1. 创建 splitter
splitter = RecursiveSplitter(
    chunk_size=1000,
    chunk_overlap=200,
    separators=["\n\n", "\n", " ", ""]
)

# 2. 创建 DocumentChunker
chunker = DocumentChunker(splitter)

# 3. 加载文档
loader = PdfLoader()
document = loader.load("/path/to/technical_paper.pdf")

# 4. 切分文档
chunks = chunker.chunk_document(document)

# 5. 验证结果
print(f"Generated {len(chunks)} chunks")
for i, chunk in enumerate(chunks[:3]):  # 显示前 3 个
    print(f"\nChunk {i}:")
    print(f"  Position: {chunk.start_offset} - {chunk.end_offset}")
    print(f"  Length: {len(chunk.text)}")
    print(f"  Preview: {chunk.text[:100]}...")
```

### 设计哲学
> **"语义完整性 > 固定 overlap 大小"**

对于 RAG 系统，我们选择优先保留语义边界（段落、章节、代码块），而不是追求固定的 overlap 大小。这个设计决策基于以下考虑：

1. **用户需求**：技术文档的查询通常与语义单元相关
2. **召回率**：语义完整的 chunk 更容易被检索到
3. **用户体验**：返回的答案更自然，不突兀
4. **可解释性**：保留结构便于理解和调试
